# WTT runtime compatibility check

Checked against the installed SPT 4.1.5 runtime on 2026-09-12.

## Observed runtime identities

| Component | Server GUID | Server-reported version | Installed assembly |
| --- | --- | --- | --- |
| WTT Armory | `com.wtt.armory` | `2.0.5` | `WTT-Armory` `2.0.5.0` |
| WTT Content Backport | `com.wtt.contentbackport` | `2.0.1` | `WTT-ContentBackport` `2.0.1.0` |
| WTT CommonLib | `com.wtt.commonlib` | `3.0.6` | `WTT-ServerCommonLib` / `WTT-ClientCommonLib` `3.0.6.0` |

The Armory files installed under `WTT-Armory` and `WTT-ArmoryClient` identify themselves as `2.0.5`, not `3.0.0`. Item Intelligence does not branch on this version or GUID.

## Compatibility result

Item Intelligence needs no WTT-specific adapter or dependency. Its server snapshot enumerates the final SPT `TemplateTable.Items`, quest table, hideout table, production recipes, trader barter schemes and price table after mod data has been registered. The client indexes every resulting record by normalized template ID. This covers Armory and Content Backport items without a hand-maintained template catalog.

Phase 34 uses representative template IDs taken from the installed Armory and Content Backport data only as fixtures. It proves generic FIR inventory, active/future quest, hideout, single-allocation, value, background, craft/barter and unknown-template fallback behavior. Production code contains no WTT item list or mandatory WTT reference.

The latest server startup loaded all three WTT server modules and Item Intelligence successfully, and the focused WTT/Item Intelligence error scan was empty. The installed Armory and Content Backport client DLLs were not present in the latest BepInEx `Loading [...]` sequence, so their client-side startup remains a separate installation/runtime observation; Item Intelligence compatibility uses their server-registered item data and does not depend on either client plugin.
